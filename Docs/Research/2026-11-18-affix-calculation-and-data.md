별도로 열람한 [오래된 Mechanics thread](https://www.pathofexile.com/forum/view-thread/11707)는 본문에서 유지보수 중단을 명시한다. 그 글의 과거 난도·저항·방어·젬 규칙을 현행 사양이나 새 수치표의 근거로 사용하지 않는다. PoEDB의 동적 페이지와 오래된 공식 글을 최신 단일 패치의 완전한 규칙으로 합치지 않는다.

## 자체 기획에 사용할 해석

옵션의 수치만 적지 않고 적용 대상·합산/곱셈·출발 성능·최종 효과를 구분하면 장비 교체의 이유를 설명할 수 있다는 것이 이번 기획 해석이다. 캐릭터의 주문 피해와 원소 피해가 같은 화염 주문에 적용되는 경우를 예로 들어 어떤 증가가 같은 단계에 합산되는지 보여 주려 한다.

명중도 생략, 방어도 A/(A+1000)와 회피 E/(E+1000), 각 상한·저항·막기·보호막/회복의 초기 값, 기반 성능·특성 수치·옵션 34종과 7단계 범위는 **우리 게임의 자체 미승인 제안**이다. 이 공식을 PoE의 현재 방어 공식이라고 소개하거나 PoE의 수치표를 반입하지 않는다. 실제 재미·난도·성장 시간을 검증한 결과도 아니다.

기존 [커뮤니티 빌드 연구](PoE1/Community-Cases.md)는 빌드가 성립하는 조건·전환 시점·실패 원인·업그레이드 순서를 공략이 보완한다는 해석에 사용한다. 이번에는 새 커뮤니티 표본으로 현재 빌드 성능이나 드롭 확률을 추정하지 않았다.

## 대안·권장 적용 범위

대안은 명중도·다양한 피해 유형·피해량에 반응하는 방어 계산과 자원 유지까지 먼저 구성하는 방식이다. 빌드의 의존 관계를 넓게 만들 수 있지만 첫 옵션의 의미와 실패 원인을 설명할 범위가 커진다.

우선 권장하는 것은 장비 자체/캐릭터 적용과 합산/별도 곱셈을 구분하고, 공격·주문 명중과 세 방어 방식·막기/저항·회복을 첫 데이터 범위로 제한하는 제안이다. 후보 목록·표시 단위·허용 단계·최종 효과를 게임 안에서 연결하려는 목적이다. 승인 전에는 정본 시스템이나 프로토타입의 전제로 사용하지 않는다.

Unity 6000.3.11f1의 C# 프로젝트에 Lua 기반 PoB를 직접 넣는 호환성은 없다. 참고할 부분은 계산 단계와 결과 근거의 분리라는 접근이며 실행 코드·오픈소스 패키지를 도입하지 않는다. 실제 장비/전투 구현 때 현재 코드와 Unity 공식 기술 문서를 조사하고 변경 범위·검증 계획을 제안한다.
