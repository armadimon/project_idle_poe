## 기획을 구체화하는 순서

| 단계 | 답할 질문 | 문서와 산출물 |
| --- | --- | --- |
| L0 방향 | 어떤 경험을 만들고 누구에게 제공하는가 | 현재 방향, 콘셉트 결정 |
| L1 규칙 | 전투와 장비·스킬 조합이 어떻게 작동하는가 | 시스템별 규칙, 예외와 상호작용 |
| L2 플레이 구성 | 어떤 순서로 무엇을 플레이하는가 | 시작 흐름, 도전과 콘텐츠 구성 |
| L3 데이터 | 어떤 항목과 단위, 수치가 필요한가 | 데이터 규격, 승인된 수치와 가설 |
| L4 검증 | 규칙이 구현되고 의도한 경험이 나타나는가 | 시뮬레이션, 플레이 결과와 수정 제안 |

계층은 정보를 구분하는 기준이다. 아직 합의하지 않은 하위 사항을 상위 문서에 끼워 넣지 않는다. 시스템이나 콘텐츠를 결정할 때도 먼저 확정한 방향을 확인한다.

## 결정 한 건을 진행하는 절차

1. 관련된 승인 결정과 아직 미정인 사항을 읽는다.
2. 한 번에 판단할 수 있는 범위로 질문을 정한다.
3. 선택지의 플레이 경험, 장단점, 개발 부담과 권장 이유를 제안한다. 추천은 승인과 구분한다.
4. 사용자 답변을 기다린다. 애매한 답변은 범위를 다시 확인한다.
5. 확인받은 항목만 결정 파일에 기록한다. 승인 근거와 관련 결정, 영향을 받는 문서를 연결한다.
6. 관련 기획을 갱신하고 형식과 링크를 검사한다. 재미나 밸런스의 검증 결과는 실제 실험 뒤 별도로 기록한다.

결정 상태는 `proposed`, `approved`, `superseded`로 나눈다. `proposed`는 검토용이며 구현의 전제가 아니다. 승인된 내용을 수정할 때는 새 결정을 확인받고 기존 결정은 `superseded`로 남긴다.

## 결정 파일 규격

`Decisions/DEC-번호-주제.md`에 결정 하나를 기록한다. 파일 첫 부분은 `---` 사이에 다음 항목을 둔다. 메타데이터는 외부 YAML 파서 없이 검사할 수 있도록 **한 줄에 `키: JSON 값`**으로 작성한다. 일반적인 YAML 전체 문법은 지원하지 않는다.

| 키 | 형식 | 의미 |
| --- | --- | --- |
| `id` | `DEC-0001` 형식 문자열 | 바뀌지 않는 결정 주소 |
| `title` | 문자열 | 결정한 주제 |
| `layer` | 0부터 4까지 정수 | 기획 단계 |
| `status` | 상태 문자열 | 제안, 승인, 대체 여부 |
| `date` | `YYYY-MM-DD` 문자열 | 결정 기록일 |
| `depends_on` | 결정 ID 배열 | 전제로 삼은 결정 |
| `approval` | 객체 또는 `null` | `by`, `date`, `evidence`로 사용자 확인 근거 기록 |

`approved`와 `superseded`에는 `by: "user"` 및 날짜와 사용자 확인 근거가 필요하다. 자동 검사는 빈 근거를 걸러낼 수 있지만 실제로 그 승인이 있었는지는 기록자가 원 대화와 대조해야 한다.

## 형식 검사와 게임 검증

```sh
python3 Tools/validate_design.py
```

이 명령은 결정 메타데이터, 승인 근거 필드, 중복 ID, 결정 참조와 순환 의존, 문서의 로컬 파일 링크, 원본 참고자료의 커밋과 서브모듈 연결을 검사한다. 링크의 제목 앵커, 외부 URL의 접속 여부와 기획의 의미는 검사하지 않는다.

게임의 재미와 밸런스는 문서 형식 검사와 별개다. 관련 기획을 확인받은 뒤 [검증 계획](Templates/experiment.md)을 구체화하고, 실제 결과를 얻었을 때만 검증 완료로 기록한다.
